# Change and Fix Reports

After **any** fix or change, the operator must receive a detailed report of what was wrong (or what changed) and how it was addressed. This applies to:

1. **This repository** — Cursor/engineering work (chat report after every change)
2. **The running Proxmox agent** — every executed action, failed/partial operation, and closed incident

Reports are persisted. They are not only a chat reply. Delivery through extra channels (email, etc.) uses `NotificationPort` and is optional; storage in the agent database is mandatory once that code exists.

Secrets, passwords, tokens, and private keys never appear in reports.

## Engineering reports (Cursor / PRs)

After any code or document change in this repo, the assistant must post a report in the conversation using this shape:

```
## Change report

- Report ID: (conversation date + short slug, e.g. 2026-09-20-change-reports)
- Date/time: (ISO-8601)
- Scope: files / area
- What was broken (or missing):
- Root cause / why it was that way:
- How it was fixed:
- What was verified:
- Residual risk / follow-up:
- Related docs or tests:
```

If nothing was broken (feature or process add), say that explicitly under “What was broken” and still describe the change.

Do not claim tests passed unless they were run. Do not claim Proxmox actions succeeded unless verified.

## Product reports (running agent)

The agent must produce a **ChangeReport** (or an **Incident** report when the work started from an error/alert) whenever:

- An approval reaches a terminal execution state (`succeeded`, `failed`, `partial`)
- An inventory/config change is applied in the agent DB in a way that operators need to see (documentation overlay is a minor change record, not a full incident)
- A troubleshooting investigation is closed
- A job that was meant to mutate infrastructure finishes

Chat may summarize; the canonical report is stored and exportable (Markdown, HTML, JSON, CSV; PDF later).

### Required fields

| Field | Purpose |
|---|---|
| Report / incident ID | Stable identifier |
| Date and time (UTC) | When it started and when it closed |
| Affected system | Node, VMID, name, kind — never guessed |
| What was broken | Original error, alert, or stated problem |
| Investigation steps | What was inspected |
| Evidence | Log excerpts, API results (redacted) |
| Likely cause | Facts vs assumptions labeled |
| Proposed solutions | With risk |
| Approved actions | Approval IDs |
| Commands or API calls executed | From the allowlist preview |
| Results | Verified outcome; `ok` / `failed` / `partial` |
| How it was fixed | What actually changed |
| Rollback actions | If used or still available |
| Lessons learned | Optional but required when closing an incident |

Simulated work is labeled **SIMULATED** on the report banner and `simulated=true` on the record.

### Delivery

| Channel | When |
|---|---|
| UI Reports / Incidents pages | Always, once Phase 8 UI exists; ChangeReports from Phase 5+ execution |
| `GET /api/v1/reports/changes` and `GET /api/v1/change-reports/{id}` | Always |
| Chat | Summary + link/id after execution |
| `NotificationPort` | If not `null`; default `log` adapter writes the report id to structured logs |

There is no auto-execute mode, so a “fix” in production always has an approval behind it. The report is generated by the execution handler, not by the LLM.

### Timing

- Phase 5: execution writes a change report row (even if UI export is thin)
- Phase 8: full incident pack, scheduled exports, CSV/HTML/Markdown
- Until then, engineering reports in Cursor chat satisfy this requirement for repository work

## What is not a substitute

- A one-line commit message
- An audit row without the narrative fields above
- Model prose that is not stored as a report record (for the running agent)
