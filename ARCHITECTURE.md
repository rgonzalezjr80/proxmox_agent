# Architecture

Local-first AI agent for inventory, documentation, monitoring, analysis, and (later) approved administration of a Proxmox homelab cluster.

This document is the source of truth for system structure. Implementation must follow it. Privileged infrastructure actions are never invoked directly by the language model.

## Status

Phase 1 (planning documents only). No application code exists yet.

## Goals

- Run entirely inside the lab. Cloud services stay off unless explicitly configured and approved.
- Start in read-only mode. Write, administrative, and destructive capabilities are added one action at a time behind approval.
- Prefer inspection over action. Fail closed when identity, approval, or connectivity is uncertain.
- Keep a complete audit trail of commands, API calls, approvals, rejections, and verified results.

## Confirmed stack

| Concern | Choice |
|---|---|
| Language | Python 3.12 |
| HTTP API and app | FastAPI + Pydantic Settings |
| ORM / migrations | SQLAlchemy 2.x + Alembic |
| Database | SQLite by default; Postgres-swappable later via SQLAlchemy |
| UI | Jinja2 + HTMX + a small amount of CSS (no SPA) |
| LLM | Ollama via an OpenAI-compatible client; fail-safe if Ollama is down |
| Proxmox access | `httpx` behind a `ProxmoxClient` protocol (not bound to `proxmoxer`) |
| Jobs | In-process scheduler (APScheduler) behind a queue interface; no Redis/Celery in v1 |
| Secrets | Environment-provided master key; application-encrypted secret store |
| Deploy | Docker Compose on a dedicated Linux VM in the lab, not on the hypervisors |

## Design principles

1. **Tool boundary.** The model may only propose allowlisted tools. It cannot open a raw HTTP client, shell, or database session.
2. **Policy before execution.** Validation, RBAC, feature flags, kill switch, approval, and audit wrapping sit between tools and adapters.
3. **Unique targets.** Tools require a unique guest/node/resource identifier. Ambiguous names force clarification. The agent never guesses.
4. **Untrusted data.** Logs, VM notes, error pastes, screenshots OCR, and websites are data, not instructions.
5. **Verified results.** An action is not reported as successful until the handler checks post-conditions.
6. **Replaceable adapters.** Proxmox, LLM, notifications, guest OS, and job backends are protocols with test doubles.
7. **Destructive defaults are forbidden.** Missing config means deny, not allow.

## Layer responsibilities

### Web interface

Server-rendered pages and HTMX partials for:

- Inventory (cluster, nodes, guests, storage, networks)
- Monitoring and alerts
- Approvals (preview, decide)
- Audit log
- Reports
- Configuration (non-secret)
- Jobs and task status
- Chat

Every mutating screen must show: understood intent, exact target, proposed operation, expected impact, risk, prerequisites, API/command preview, backup/snapshot plan, rollback plan, and the approval required.

### API layer

Versioned JSON API under `/api/v1`. OpenAPI is generated by FastAPI. Human overview lives in [API_DESIGN.md](API_DESIGN.md). Health endpoints are unauthenticated; everything else requires a session or token.

### AI orchestration

A tool-calling loop that:

- Loads system rules that cannot be overridden by user or retrieved content
- Wraps operator-pasted logs, VM descriptions, and tool outputs in untrusted delimiters
- Resolves targets against inventory; asks when zero or many matches exist
- Emits structured “what I understood” summaries before any mutating proposal
- Never marks an action complete based on model text; only handler verification counts

If Ollama is unavailable, chat returns a clear degradation message. Inventory, monitoring, and approvals continue to work.

### Application services

Plain Python services, independent of FastAPI and of the LLM:

- `InventoryService` — sync, query, documentation records
- `MonitoringService` — thresholds, alerts, acknowledgements, suppressions, maintenance windows
- `ApprovalService` — request lifecycle, re-auth, expiry
- `AuditService` — append-only, hash-chained events
- `ReportService` — Markdown, HTML, JSON, CSV (PDF later if practical)
- `JobService` — scheduled and on-demand work
- `IncidentService` — investigations tied to conversations

### Tools and execution handlers

Each tool is a typed object:

- Name and action family (used by feature flags), e.g. `vm.start`
- Input schema (Pydantic)
- Risk class
- Dry-run / preview producer (exact method, path, body)
- Handler that talks only to adapters
- Post-condition check

Unlisted tools do not exist. There is no “run arbitrary command” tool.

### Integration adapters

| Protocol | v1 adapter | Notes |
|---|---|---|
| `ProxmoxClient` | HTTPS `httpx` to cluster API `:8006` | Token auth; TLS verify on; optional custom CA |
| `LlmProvider` | Ollama OpenAI-compatible API | Optional `CloudLlmProvider` exists in code later but stays disabled |
| `NotificationPort` | `Null` and `Log` | Email/Push/etc. added later without changing callers |
| `JobQueue` | APScheduler / asyncio | Swap later without changing services |
| `SecretStore` | Encrypted SQLite-backed blobs | Master key from environment |
| `LinuxGuestClient` | Not implemented until Phase 7 | SSH via allowlisted commands |
| `WindowsGuestClient` | Not implemented until Phase 7 | WinRM or equivalent, allowlisted |

### Data

SQLite file on a persistent volume. Alembic migrations from the first schema. See [DATA_MODEL.md](DATA_MODEL.md).

### Kill switch

Three equivalent controls, any of which disables all mutating tools immediately:

1. Config flag `AGENT_EMERGENCY_STOP=true`
2. Presence of a well-known file (default `data/EMERGENCY_STOP`)
3. Authenticated UI button and `POST /api/v1/emergency-stop`

Read-only inventory and audit remain available. Clearing the stop requires an admin and is itself audited.

## Default operating mode

`AGENT_MODE=read_only`.

Feature flags exist per action family (`vm.start`, `vm.delete`, `user.create`, …). An action is executable only when:

1. Mode is not forcing read-only for that family
2. The flag is enabled
3. The caller’s role permits it
4. The kill switch is off
5. Approval (and re-auth, if required) succeeded
6. The target resolved uniquely and still exists

## Deployment topology

```
Lab LAN
  ├── Proxmox node A  ──┐
  ├── Proxmox node B  ──┴── cluster API :8006
  ├── Guests (Windows / Linux VMs, optional LXC)
  └── Management VM (this agent)
        ├── Docker Compose: app + volume for SQLite / encrypted secrets
        └── Ollama on the same VM or another lab host (never required for read APIs)
```

The agent is not installed on the hypervisors. It uses the Proxmox API as a client. Initial credential is a token with `PVEAuditor` only. Privileged tokens are not configured until Phase 6.

## Failure modes

| Failure | Behavior |
|---|---|
| Ollama down | Chat and analysis unavailable; inventory, monitoring, approvals still work |
| Proxmox API down | Sync and mutating tools fail closed; last inventory remains readable and is marked stale |
| Database down | Process unhealthy (`/ready` fails); no writes; no false success |
| Secret store / master key missing | Process refuses to start or refuses adapters that need secrets |
| Ambiguous target | No tool call; operator is asked to disambiguate |
| Partial Proxmox task | Handler records partial failure, does not claim success, suggests recovery |
| Kill switch on | Mutating tools denied; reason shown |

## Out of scope for v1

- Multi-tenant SaaS
- Installing or managing the Proxmox host OS itself
- Automatic remediation without approval
- Cloud-hosted models, vector DBs, or telemetry
- Redis, Kafka, or other extra runtime infrastructure
- Directory/SSO (local users first)
